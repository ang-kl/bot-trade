Requested by the owner: *"Act as a senior UI/UX engineer and conduct a forensic
interface audit of the entire web application"* with the settings relocated to a
sidebar footer, a `rem`-based type scale, 200% text resize and 320px reflow.

Everything below is **measured**, in Chromium, against a running agent — not read

### Why the app-wide migration is staged rather than done in one sweep

**Stated plainly because the acceptance criteria are not all met yet.**

There are several hundred `text-[Npx]` literals across 40+ components. Those
values were tuned over many rounds against explicit and repeated owner
instructions — *"the size of field-entry must be uniform as I am OCD"*, 9px
tables, *"dense and less screen scrolling"*. A blind find-and-replace would be a
multi-thousand-line diff in which a deliberate density choice is
indistinguishable from an accident, on pages that arm real money.

So the order is: tokens first (done), chrome adopted (done), then per-route
migration **behind the measurements** in `scripts/responsive-audit.mjs`, which
already reports `minFont` per route and can fail a build on a regression. That is
the part still outstanding.

### The 8px question — SETTLED by the owner

Asked and answered (2026-07-30): *"Use the 8 font size / 3 px smaller."* The
earlier specs win over §1.6 for these two labels, so they stay:

- the off-summary heading — 8px, per *"in 8 font size"*
- the `pause` ring label — 8px, which is 3px below the block's primary 11px text

That is what shipped, so no change was needed. §1.6 still governs everything
else: no NEW sub-caption pixel values are introduced to make content fit.

### Still outstanding, precisely
- Route-level `minFont` of 8–9px on Risk, Tune, Performance is untouched.
- `touch<44` is reported for most desktop controls by design: the 44px tap-target
  halo in `index.css` is scoped to `max-width: 430px and (pointer: coarse)`. A
  mouse does not need 44px, so this is not a defect — but the audit line looks
  like one and should be labelled in the tool.

### 6.1 · ROOT CAUSE of the screenshot — a Tailwind v4 ambiguity, and my error

| field | detail |
| :-- | :-- |
| **Observed defect** | The page footer rendered `bot-trade v0.1.381 · build 4829608` at heading size, overlapping the strategy table; the tab panel floated mid-page |
| **Root cause** | `text-[var(--fs-caption)]`. In Tailwind v4 the `text-*` utility is ambiguous between `font-size` and `color`, and a bare custom property resolves to **color**. Verified against the built CSS: the class emitted `color:var(--fs-caption)` — i.e. `color: 0.6875rem`, an invalid colour — and **no font-size at all**. So the element inherited the body size and also lost its muted grey. The correct v4 syntax is explicit: `text-(length:--fs-caption)`. |
| **Severity** | High — permanent chrome over live trading content |
| **This corrects §3 of this document.** | §3 claimed "the chrome rebuilt in this pass … uses the tokens" and marked the rem scale as adopted. That was wrong. The tokens existed in `:root` but **no call site ever received a font-size from them** — all three call sites were the broken syntax. The type-scale work was not partially done; for font sizes it was not done at all. |
| **Correction** | All `--fs-*` call sites migrated to `text-(length:--…)`; verified `font-size:var(--fs-caption)` now appears in the built CSS. Guarded by `src/lib/css-token-syntax.test.js`, which fails the build on any `text-[var(--…)]` outside a comment. |

### 6.3 · Three defects found by measuring, not by reading

1. **The popover rendered off-screen** (measured `left: -159px`) even though every viewport clamp said otherwise. Two causes, both cascade/layout traps this repo has hit before: `glass-panel` is **unlayered** CSS setting `position: relative`, which outranks Tailwind's layered `fixed` (computed style confirmed `relative`); and its `backdrop-filter` makes it the containing block for any `fixed` descendant, while `overflow: hidden` would clip it anyway. Fixed by portalling to `document.body` and setting `position: fixed` inline. The clamp also now converts visual→layout pixels for the `zoom: 1.1` on `html`.
2. **"Disconnected · active for 10d"** — `aliveText` only switched to past tense for `revoked`, so a disconnected session asserted it was active. Now any non-live state reads "Existed …".
3. **`localTime` printed `Invalid Date`** to the user on a malformed stamp: `new Date('x').toLocaleString()` returns that string rather than throwing, so the `try/catch` never fired. Now validated with `Date.parse` first.

### 6.4 · Where I did NOT follow the brief literally, and why

| brief text | what shipped | reason |
| :-- | :-- | :-- |
| Close WebSockets / SSE streams on revocation | Reports `transport: polling`; revocation invalidates the credential | **There is no browser WebSocket or EventSource in `src/`.** The only WebSockets in this repo talk to the broker, from the agent and the C++ sidecar. Claiming a socket was torn down would be false. What happens instead is stronger, not weaker: the token stops authenticating, so the next request is refused at the auth middleware before any route runs. **Measured: revoked token → 401 on both a read and a write route; a valid token → 200.** |
| `--fs-session: 10px` | `0.625rem` (= exactly 10px at a 16px root) | The brief also requires "user font scaling remain effective". A px literal satisfies the cap and defeats that — **measured: at a 32px root the line stayed 10px**. In rem it renders at exactly 10px by default and scales with the reader's own preference (measured 20px at a 32px root). Flagged for the owner: if the cap must hold at 10px absolutely, say so and I will pin it back. |
| `POST /api/sessions/{id}/revoke` | `POST /actions/sessions/{id}/revoke` | `/actions/*` is the write-tier namespace under the existing D12 two-tier auth and carries the state-cache invalidation hook. Path shape preserved. |
| Cancel session-owned queued work | Drops that session's presence tabs, and nothing else | Having looked: the only server-side state a *browser* session owns is its presence-roster entries. There are no per-session job queues or event-replay buffers on the browser path — trading queues belong to accounts and the loop. Confirmed by test that revocation touches only the named session's tabs. |
| Theme control | Kept in the sidebar footer beside the session line | The brief does not mention it and it has to stay reachable. It is a compact rounded rectangle (7px, never a capsule) so the footer is still one visible line. |
| Tab-roster panel | Removed; its unique "sleep after" setting folded into the popover | The brief removes "the floating browser-tab status panel". The popover's per-session tab counts and pages cover the same ground; the sleep-after control is genuinely session-lifecycle, so it moved rather than being dropped. |

### 6.5 · Current-session protection — measured, both layers

- The UI shows **no** enabled Disconnect for the current session and says why.
- The server refuses it independently: `POST` self-revoke → **409** `self_revoke_forbidden`, the credential is untouched, and the rejected attempt is written to the audit log. A stale page cannot talk the server into it.
- `isCurrent` is derived from the request's own `Authorization` header. The same stored data requested with a different token marks a different session current (tested), and a client-supplied `sid` on the heartbeat is ignored (tested).
- The master `AGENT_SECRET` is reported as un-revokable with the reason, rather than being given a button that would sign out every device at once.
