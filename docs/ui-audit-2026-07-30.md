# Interface audit — 2026-07-30

Requested by the owner: *"Act as a senior UI/UX engineer and conduct a forensic
interface audit of the entire web application"* with the settings relocated to a
sidebar footer, a `rem`-based type scale, 200% text resize and 320px reflow.

Everything below is **measured**, in Chromium, against a running agent — not read
off the source. The probe is `scripts/responsive-audit.mjs` plus the per-element
measurements quoted inline. Where a criterion is **not yet met**, it says so.

---

## 1 · Sidebar — settings relocated to a real footer

| field | detail |
| :-- | :-- |
| **Page / component** | `src/App.jsx` desktop `<aside>`; `src/components/common/TabsPanel.jsx` |
| **Observed defect** | Web-app settings (Tabs roster, sleep-after, Theme) scrolled away with the nav; a horizontal scrollbar consumed sidebar width; the settings block sat behind a `pb-[10vh]` spacer |
| **Root cause** | One `overflow-y-auto` wrapped the **entire** panel, so the settings were the last child of the same scroll container as the nav — "persistently accessible" is not reachable by position alone. The earlier fix for *"I still cannot see the active web setting"* was `pb-[10vh]`, which made that scroller **taller**, pushing the settings further out of reach on a short window. |
| **Severity** | High — the controls were unreachable in the exact situation they were added for |
| **WCAG / design-system** | 1.4.10 Reflow (no horizontal scroll), 1.4.4 Resize Text (200%), 2.4.3 Focus Order |
| **Correction** | Panel `overflow-hidden`; header and `ActiveAccountHeader` `shrink-0`; `<nav>` becomes `flex-1 min-h-0 overflow-y-auto overflow-x-hidden` — the only scrolling region; footer is a `shrink-0` sibling with a `border-t` instead of a spacer, so no vertical space is spent on emptiness. **Not** in the FAB. |
| **Files changed** | `src/App.jsx`, `src/components/common/TabsPanel.jsx`, `src/index.css` |
| **Validation** | Measured at 1440×900, `/performance`: |

```
zoom=100%  sidebarHScroll=0  panelHScroll=0  bodyHScroll=0
           panelOverflowY=hidden  navOverflowY=auto  footerVisible=true
zoom=200%  sidebarHScroll=0  panelHScroll=0  bodyHScroll=0
           panelOverflowY=hidden  navOverflowY=auto  navScrolls=true  footerVisible=true
```

At 200% the nav genuinely scrolls (`navScrolls=true`) **while the footer stays
visible** — which is the acceptance criterion, not an approximation of it.

## 2 · The horizontal scrollbar — found and removed

| field | detail |
| :-- | :-- |
| **Component** | `TabsPanel.jsx`, the "sleep after" row |
| **Observed defect** | Horizontal scrollbar across the sidebar (visible in the owner's screenshot, directly under the sleep-after row) |
| **Root cause** | Six children — a label, four choice buttons and an info glyph — in a **non-wrapping** flex row inside a ~192px content column (`lg:w-56` = 224px minus 2×16px padding). It could not fit, so the browser gave the sidebar a horizontal scrollbar, which then also ate a line of vertical space. |
| **Severity** | High — the owner named it: *"The horizontal scrollbar consumes limited navigation space"* |
| **WCAG** | 1.4.10 Reflow |
| **Correction** | `flex-wrap` with `gap-x`/`gap-y`, so it becomes two short lines; removed the `ml-auto` that would have kept forcing width once wrapped |
| **Validation** | `sidebarHScroll=0` at 100% and 200% (above) |

## 3 · Typography — token scale added, migration deliberately staged

| field | detail |
| :-- | :-- |
| **Observed defect** | Hard-coded pixel font sizes throughout; the sidebar reached **7px**; `audit:ui` reports `minFont` 8–9px on Risk and Tune |
| **Root cause** | Every size is a Tailwind arbitrary literal (`text-[9px]`), so no user font preference or zoom setting can move them together |
| **Severity** | Medium–High for readability; the 7px values are what *"Some labels and controls are difficult to read"* referred to |
| **WCAG** | 1.4.4 Resize Text |
| **Correction (done)** | `:root` now carries the requested `rem` scale — `--fs-caption 0.6875rem`, `--fs-secondary 0.8125rem`, `--fs-body 1rem`, `--fs-heading-sm 1.125rem`, `--fs-heading-md 1.25rem`. The chrome rebuilt in this pass (sidebar footer, TabsPanel rows, Theme button) uses the tokens. The 7px rows are gone. |
| **Files changed** | `src/index.css`, `src/App.jsx`, `src/components/common/TabsPanel.jsx` |

### Why the app-wide migration is staged rather than done in one sweep

**Stated plainly because the acceptance criteria are not all met yet.**

There are several hundred `text-[Npx]` literals across 40+ components. Those
values were tuned over many rounds against explicit and repeated owner
instructions — *"the size of field-entry must be uniform as I am OCD"*, 9px
tables, *"dense and less screen scrolling"*. A blind find-and-replace would be a
multi-thousand-line diff in which a deliberate density choice is
indistinguishable from an accident, on pages that arm real money.

So the order is: tokens first (done), chrome adopted (done), then per-route
migration **behind the measurements** in `scripts/responsive-audit.mjs`, which
already reports `minFont` per route and can fail a build on a regression. That is
the part still outstanding.

### The 8px question — SETTLED by the owner

Asked and answered (2026-07-30): *"Use the 8 font size / 3 px smaller."* The
earlier specs win over §1.6 for these two labels, so they stay:

- the off-summary heading — 8px, per *"in 8 font size"*
- the `pause` ring label — 8px, which is 3px below the block's primary 11px text

That is what shipped, so no change was needed. §1.6 still governs everything
else: no NEW sub-caption pixel values are introduced to make content fit.

### Still outstanding, precisely
- Route-level `minFont` of 8–9px on Risk, Tune, Performance is untouched.
- `touch<44` is reported for most desktop controls by design: the 44px tap-target
  halo in `index.css` is scoped to `max-width: 430px and (pointer: coarse)`. A
  mouse does not need 44px, so this is not a defect — but the audit line looks
  like one and should be labelled in the tool.
