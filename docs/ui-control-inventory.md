# bot-trade — UI Control Inventory (PR-F, re-derived from HEAD, 2026-09-11)

This file replaces the Phase-A hand audit that was pinned to `16defbd` (its
a11y findings were folded into the compact-M3 work and the cockpit register
in `docs/plan-execution-audit-2026-09-11.md`). What is here now is a
different question, the one owner principle 6 asks — **"UI switches are
logic-built, not for show"** — answered mechanically:

> For every control on the site that writes to the agent: does a route
> exist, does the agent read what was written, and does the site read the
> effective value back?

The table between the markers is GENERATED by `scripts/ui-control-inventory.mjs`
(`node scripts/ui-control-inventory.mjs` rewrites it; `--check` exits 1 when
it is stale) and RE-CHECKED by `src/lib/ui-control-inventory.test.js`, which
parses it and asserts against `agent/`: every listed route is declared in
`agent/routes/*.js`, every listed state key is read somewhere in `agent/`
(comment-stripped), every `'/actions/…'` literal in `src/` has a row, and no
row is HALF or DECORATIVE. A control cannot go decorative without the test
going red (CLAUDE.md failure mode #3).

## Columns

- **File:line** — the call site of the `'/actions/…'` literal in `src/`
  (tests excluded). One row per call site, so a route used from three places
  has three rows.
- **Label** — the nearest button text / `label=` / wrapper name; a heuristic
  for orientation, not a contract.
- **Route** — the literal; `${…}` segments are matched to `:param` routes.
- **Backend reads** — the `agent_state` keys the handler writes
  (`setState(db, 'key')`), each `✓` when other agent code reads the key and
  `✗` when nothing does; `via fn(db, …)` when the handler hands the write to a
  service; `executes` when it acts (broker call, table write, job start);
  `read over POST` when the POST is a query and the reply IS the value.
- **UI reads back** — the `/state/…` route the site fetches whose handler
  reads that key; else `the reply (…)` when the call site consumes the
  route's reply (`const r = await agentPost(…)`, `.then(…)`); else `poll …`
  for a background job; else `reload` when the same handler (or its wrapper —
  `run`, `save`, `toggle`, `act` — resolved transitively) re-reads the page.
- **Class** — `WIRED` (route exists · every key read or the handler acts ·
  a read-back exists) · `HALF` (route exists, a key unread or no read-back) ·
  `DECORATIVE` (no such route).

## Reads that are not writes

`agentGet('/actions/instrument-tree')` is a GET under `/actions` (the broker
catalogue); it is listed with the POSTs because the literal lives in `src/`.
The `READ_ONLY_POSTS` list in `src/lib/agent-api.js` names routes, not
controls, and is skipped by the generator.

## What the generator cannot judge

- Whether a WIRED control is *useful* — only that its value reaches the agent
  and comes back.
- Per-account overlay writes (`setState(db, acctKey(…))`) are reported as
  `dynamic key(s)`; their readers are the overlay loaders, tested in
  `agent/services/*.test.js`.
- Labels are heuristic; the file:line is the contract.
