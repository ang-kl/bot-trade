## A. ASSUMPTIONS

- `ExecEngine::placeOrder` (`cpp-exec/src/engine.cpp:282-325`) is the sole broker-facing
  order-submission function in the C++ binary; every path that reaches the broker for a
  new order — HTTP `/order`, and the VPO direct-fire path — calls this same function.
  Falsified by any other call site constructing and sending a `NEW_ORDER_REQ`.
- `agent/services/risk.js`'s `evaluateTrade` (`risk.js:474`) is the sole implementation
  of the news gate, duplicate-symbol veto, and correlation caps; no equivalent exists
  in C++. Falsified by an equivalent check found in `cpp-exec/src`.
- `order_guard.cpp`'s `validateOrder` and its JS mirror `validateExecGuard`/
  `validateOrderBracket` (`exec-engine.js:182-214`) are the only broker-side-adjacent
  safety checks that DO run uniformly regardless of order origin. Falsified by a code
  path in either language that calls `placeOrder`/`ExecEngine::placeOrder` without
  passing through these.
- Test files are evidence of intent only (K6); no test-file behavior is asserted as
  fact below.

## E. LAYER VERDICT

- **L4.1 (order submission / gating parity):** **settled, and this is the finding.** Two structurally different gating regimes coexist: the JS-originated path (`pending-orders.js:274` → `exec.placeOrder`) always clears `risk.js`'s full `evaluateTrade` before an order payload is even built, regardless of which exec engine eventually submits it (`cpp` sidecar HTTP or direct `ctrader-ws.js`). The VPO-originated path never does — it only clears the four `order_guard` checks (halt/naked/no-target/max-volume), which are necessary-but-not-sufficient compared to `risk.js`. This is not a bug in either path individually; it is a genuine two-tier authority split, confirmed by direct call-graph trace, not assumed from a comment.
- **L4.2 (idempotency):** settled as a documented design choice, not a full guarantee. No client-order-id exists; ambiguous-outcome handling refuses to retry rather than retrying safely. This is a conservative fix for a real historical incident (4x USDIDR), adequate for its stated purpose, but not "idempotent submission" in the formal sense.
- **L5.1 (SL/TP atomicity):** settled that enforcement exists and is atomic (bracket sent with the entry order, not amended in afterward); NOT settled whether the enforcing flags default on in a fresh deployment (TIER-B, DR-5).
- **L5.2 (trailing staleness):** settled as an extension of PASS 1's F-L2-05/F-L3-02 — the same unbounded-tick-age gap that affects VPO's fire site also affects the trail engine's tightening decisions, via the same in-process spot-feed tick source.
- **L5.3 (time-cap mechanism count):** NOT EVIDENCED whether one or two independent time-cap systems are live. TIER-C, DR-6.

## H. TOP 5 BY CAPITAL AT RISK (this pass)

1. **F-L4-01 — CONFIRMED: VPO-originated orders bypass `risk.js`'s news gate, duplicate-symbol veto, and correlation caps entirely, by direct call-graph trace.** This upgrades PASS 1's #1 Top-5 finding from "pending verification" to "confirmed as true." 2. **F-L5-02 — the trailing engine inherits the same unbounded tick-staleness gap as the VPO fire site**, meaning a stop-tightening decision during a spot-feed reconnect gap can act on data from before the disconnect, with no age check anywhere in the trail path.
3. **F-L4-02 — the JS-side halt/volume guard's protection is conditional on `creds.execGuard` being populated**, and whether any live caller bypasses this by hand-assembling credentials is unverified (DR-7).
4. **F-L5-03 — two independent time-cap position-close mechanisms may or may not be coordinated**, risking either a double-close race or one silently overriding the other with no log distinguishing which fired.
5. **F-L5-01 — SL/TP-required enforcement's default state (on vs. off) in a fresh deployment is unverified**, though the mechanism itself, once enabled, is correctly atomic.
