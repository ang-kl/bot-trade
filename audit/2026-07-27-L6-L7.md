## D. LAYER VERDICT

- **L6.1 (attribution):** settled — the "manual/external" ambiguity is real but already surfaced to the UI with a source breakdown, not hidden. HYGIENE only.
- **L6.2 (edge feedback loops):** settled with one real gap (Kelly never scales up, by design — F-L6-02) and one coordination question (F-L6-03, two tuning mechanisms with no documented precedence).
- **L6.3 (per-account scoping):** settled — confirmed genuinely account-scoped (postmortems inherit trade's `account_id`; `computeDecayKeys` takes an explicit `accountId`), with legacy NULL rows correctly falling back to global rather than being silently dropped. This directly addresses the demo+live coexistence concern raised earlier today.
- **L6.4 (backtest-vs-live reconciliation):** settled — genuinely wired via the Reality-gap advisory, not siloed. A confirmed strength.
- **L6.5 (correlated-loss post-mortem):** NOT EVIDENCED — only pre-trade correlation vetoes exist; no retrospective correlated-loss-clustering analysis exists anywhere in the repo.
- **L6.6 (retention):** settled — most tables are bounded by a housekeeping sweep; `trades`/`trade_postmortems` are the two unbounded exceptions (F-L6-05).
- **L7.1 (news gate):** settled — source is a single free/unauthenticated mirror (F-L7-01, TIER-B/operator judgment call), but the staleness handling on that feed is confirmed fixed and fails open correctly (F-L7-02).
- **L7.2 (spike protection scope):** settled as a genuine design question, not a bug — spike detection never blocks new entries, only speeds up scan priority and position management (F-L7-03).
- **L7.3 (slippage enforcement):** settled — measured, not enforced (F-L7-04). A real, buildable gap.
- **L7.4 (frozen-quote resistance):** settled as absent (F-L7-05).
- **L7.5 (third-party dependency surface / LLM in the hot path):** settled and reassuring — the LLM is never in the entry-order-placement path at all; its only live-position influence (exit requests) is deterministically gated to loss/breakeven-or-worse positions only (`loop.js:1217-1244`), with positive-R exit requests logged as advisory-only and never executed.
- **L7.6 (kill-switch reachability / dead-man's switch):** the most consequential verdict of this pass. Manual kill-switches exist and work in normal operation, but (a) no automated halt exists on any failure signal (F-L7-06), and (b) the manual kill-switches themselves share a single-process, single-event-loop architecture with the trading logic they're meant to stop (F-L7-07) — a genuine stuck-process scenario has no guaranteed exit.

## F. OPERATOR QUESTIONS (TIER-C)

- **OQ-3** (F-L7-03): is "bump a spiking symbol to the front of the scan queue" (faster entry into volatility) the intended posture, or should a detected spike instead impose a brief entry cooldown on that symbol until the move settles? Both are defensible; the code currently only implements the former.
- **OQ-4** (F-L7-06/F-L7-07): does the owner want an automated dead-man's switch (e.g. auto-halt `autotradeEnabled` after N missed heartbeats with no human acknowledgment) as a floor under the existing Telegram-alert-only stall handling? This is a genuine policy decision — some operators prefer "never auto-halt, always alert a human" specifically to avoid a false-positive auto-halt during a legitimate but slow market event.

## G. TOP 5 BY CAPITAL AT RISK (this pass)

1. **F-L7-06 — no automated dead-man's switch exists anywhere in the system.** A stalled controller produces an alert, never an automatic halt. Combined with PASS 1's F-L3-03 (a stalled/crashed loop also silently stops monitoring every open position), this is the largest unaddressed gap surfaced across all three passes: the system's only floor under "something is badly wrong" is a human noticing a Telegram message.
2. **F-L7-07 — every kill-switch (manual close-all, Telegram halt) shares the same single event loop as the trading logic**, so the one scenario where a human WOULD want to intervene fastest (a stuck/hung process) is exactly the scenario where the intervention path is least reliable.
3. **F-L7-04 — slippage is measured but never enforced**, despite the data pipeline already existing — the cheapest of this pass's findings to close, since no new data capture is needed, only a gate.
4. **F-L6-05 — `trades`/`trade_postmortems` have no retention sweep**, an operational (not immediate-capital) risk that compounds as trade volume grows, especially under the in-flight multi-account migration.
5. **F-L7-05 — no frozen-single-quote detector for held positions**, leaving the broker's own SL/TP as the sole backstop against a stale price silently mispricing an open position's displayed P&L (though not its actual broker-side risk, which the broker's resting orders still protect).
