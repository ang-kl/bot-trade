   `fetch()` rejects identically for an agent that is down, DNS gone, TLS

### The defects worth remembering

- **`SUM` skips NULLs.** Both daily-loss caps summed `net_pnl` over today's
  closed trades, and three closure paths leave that column NULL — including
  the broker-side close, which is the normal stop-out exit. A day of
  stop-outs summed to zero and neither cap tripped. The brake was off for
  exactly the trades most likely to be losses.
- **`Array.prototype.filter` hands the callback the ORIGINAL array.** The
  cockpit's tape de-overlap filter compared each tick against the pre-filter
  neighbour, so it never dropped anything. Reading `arr[i-1]` inside a filter
  as "the previous KEPT item" is the trap; it is the previous CANDIDATE.
- **A guard can protect against the case it disabled.** The order dedupe read
  `trades`; the ambiguous-submission path writes no `trades` row. It covered
  the retry it had turned off and missed the one that could still double.

## Evening: D14 answered, and a production flag turned off

D11 answered "harden both" → P2 shipped as #401. D14 answered with the sidecar
env flags → #402.

**The D14 consequence.** Both environments carry `VPO_ENABLED=true` and
`TRAIL_TICK_ENABLED=true`; only staging carries `VPO_SYMBOLS`. Since
`TRAIL_TICK_ENABLED` alone starts the spot feed (`cpp-exec/src/main.cpp:183-190`)
and the `/connect` teardown branch is
`if ((vpoDispatcher && !vpoSymbolIds.empty()) || trailTickEnabled)`
(`main.cpp:357`), findings **C1** and **C2** are reachable in production on
every `/connect` — and `/connect` is memoised on `(host, roster, token)`, so a
token refresh re-fires it. **P7 therefore outranks P6**, which is staging-only
until `VPO_SYMBOLS` is set in production.

**Owner decision (15:09 SGT): `TRAIL_TICK_ENABLED=false` on production** until
P7 lands. This removes the undefined behaviour without a code change: with the
flag off the teardown branch is never taken. The cost is dropping from
tick-level SL trailing to the profit keeper's own 3s ratchet —
`pushTrailConfig` returns `false` against the 503 the sidecar serves when the
flag is unset (`main.cpp:390-391`; `agent/lib/exec-engine.js:99`), and the
keeper carries on by contract. Staging keeps the flag on: if the crash is going
to happen, that is where it should be observable.

**Measured while deciding, 07:09 UTC.** `cpp-exec-production.up.railway.app/health`
answers `connected:false`, `hasCredentials:false`, `depthBookEntries:null`. The
spot feed is constructed inside the `/connect` handler, so a null
`depthBookEntries` means no feed exists there — i.e. **no `/connect` has ever
reached that sidecar**, which is what you would expect if production runs
`EXEC_ENGINE=js`. That softens the urgency but not the decision: the moment
production is switched to `cpp`, C1 fires on the first connect. I have not
confirmed that host is *the* production sidecar, nor production's `EXEC_ENGINE`
value — both are operator facts, recorded here as unverified.

Staging at the same moment: `connected:true`, roster `43097342 / 46130058 /
46979908`, `depthBookEntries:0` (feed up, no depth subscribed —
`DEPTH_FEED_ENABLED` is off).

`depthBookEntries` is the cheap public check that the flag change took effect:
