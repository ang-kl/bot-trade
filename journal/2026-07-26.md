## Two things that were wrong and are now corrected in the repo

1. **The "Agent unreachable" toast asserted a cause it could not know.**
   `fetch()` rejects identically for an agent that is down, DNS gone, TLS
   refused, a phone dropping Wi-Fi mid-request, and a reply that never arrived
   because the agent was busy. The copy now says only what is known, and
   distinguishes idempotent reads ("nothing was changed") from order actions
   ("this may or may not have been carried out — check the position before
   retrying"). Order actions are deliberately never aborted or retried.

2. **The reply serial had no reproducible source.** It does now:
   `npm run serial` reads the session transcript from disk. Measured on session
   `ad9d1f6f` at 01:00 UTC — **1,773 reply turns**, 404 owner turns, 10,558
   assistant entries, 28 compact events, 172 MB. The serial is rebased so 1,773
   was the last reply. The earlier note in CLAUDE.md claiming `№ 176` was a
   fabrication with no ledger behind it was itself wrong: the transcript
   carries 134 stamped headers running `№ 1` → `№ 145` across 22–25 July. The
   real fault was undercounting — only replies judged "substantive" were
   stamped.
